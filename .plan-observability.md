# Plan: Observability & Type Safety Improvements

## Overview

Внедрение observability (token tracking, error logging) и исправление type generation для AI Life OS. Выбран модульный подход с созданием `utils/observability.ts` и сохранением метрик в отдельную таблицу `usage_metrics`. База данных пустая — можно добавить таблицу в init SQL без миграций.

**Ключевые решения:**
- Modular observability вместо inline callbacks — баланс простоты и расширяемости
- Отдельная таблица `usage_metrics` вместо message metadata — чистая аналитика
- Property-based тестирование — соответствие существующим паттернам

## Planning Context

### Decision Log

| Decision | Reasoning Chain |
|----------|-----------------|
| Modular observability over inline | Inline callbacks = console.log only -> нет persistence -> нет аналитики costs -> modular позволяет persistence + легко расширить webhooks/analytics в Phase 2 |
| Separate `usage_metrics` table over message metadata | Message metadata смешивает concerns -> отдельная таблица = чистые SQL aggregations + независимый retention policy -> лучше для cost tracking dashboard |
| `onFinish` callback over manual tracking | Manual tracking требует wrap каждого stream chunk -> onFinish вызывается SDK автоматически с aggregated usage -> меньше кода, надёжнее |
| `onError` callback + existing catch | onError ловит LLM-level errors (rate limits, model unavailable) -> existing catch ловит workflow errors (DB, abort) -> полное покрытие ошибок |
| Property-based tests over example-based | Existing config.test.ts uses fast-check -> consistency across codebase -> property tests cover more edge cases (token counts, error types) |
| Add table to init SQL over migration | Database is empty (Phase 1) -> no data to migrate -> simpler to recreate with new schema -> avoids migration tooling complexity |
| Token count handling: store all three values | totalTokens may exceed inputTokens + outputTokens when reasoning tokens present (Claude Opus extended thinking) -> store all three as-is to preserve actual cost data -> aggregation uses totalTokens for actual billing -> validation: reject negative/null, accept totalTokens >= inputTokens + outputTokens |
| Retention policy: indefinite retention | User confirmed: retain all usage_metrics indefinitely for historical cost analysis -> enables long-term trend analysis and budgeting -> storage cost acceptable for analytics value -> future: add archive job if storage becomes concern |
| CASCADE DELETE for metrics | User confirmed: usage_metrics cascade deletes with conversation for privacy compliance -> when user deletes conversation (privacy/cleanup), cost metrics also removed -> analytics sacrifice for GDPR-style data minimization -> alternative: anonymize conversation_id instead of CASCADE would preserve cost data |
| Error log structure format | Structured error logs include: timestamp (ISO8601), level (ERROR), context (workflow name), message (error.message), stack (error.stack), metadata (conversation_id when available) -> enables monitoring tool integration (CloudWatch, Sentry) -> consistent format across all LLM error paths |

### Rejected Alternatives

| Alternative | Why Rejected |
|-------------|--------------|
| OpenTelemetry integration | Over-engineering для Phase 1 -> требует инфраструктуру (Jaeger/Zipkin) -> отложить до production scale |
| Token tracking в message metadata | Смешивает message content с analytics -> усложняет queries -> metadata уже используется для error info |
| `toUIMessageStreamResponse()` | Требует refactor всего streaming pipeline -> current custom stream работает и понятен -> breaking change без significant gain |
| Console-only logging | Нет persistence -> нельзя анализировать costs -> бесполезно для production observability |

### Constraints & Assumptions

- **Technical**: Vercel AI SDK 4.0 поддерживает `onFinish`/`onError` callbacks
- **Database**: Supabase PostgreSQL, база пустая — можно пересоздать
- **Testing**: Vitest + fast-check (property-based) — существующий паттерн
- **Scope**: Только улучшения existing code, НЕ Phase 2 features (agents, tools, RLS)

### Known Risks

| Risk | Mitigation | Anchor |
|------|------------|--------|
| `onFinish` не вызывается при abort | Проверить AbortController handling, возможно нужен `onError` fallback | packages/ai/src/workflows/chat.workflow.ts:L112-118 (existing abort handling) |
| Usage metrics table performance | Добавить index на conversation_id + created_at для aggregation queries | Будет в init SQL |
| Type generation может показать schema drift | Запустить `pnpm db:generate` первым, исправить mismatches до других изменений | - |

## Invisible Knowledge

### Architecture

```
HTTP Request (POST /api/chat)
       |
       v
+------------------+     +-------------------+
| chatWorkflow()   |---->| streamText()      |
| (orchestrator)   |     | (Vercel AI SDK)   |
+------------------+     +-------------------+
       |                        |
       |                        | onFinish(usage)
       |                        | onError(error)
       v                        v
+------------------+     +-------------------+
| updateMessage()  |     | observability.ts  |
| (status update)  |     | (token tracking)  |
+------------------+     +-------------------+
       |                        |
       v                        v
+------------------+     +-------------------+
| messages table   |     | usage_metrics     |
| (content, status)|     | (tokens, costs)   |
+------------------+     +-------------------+
```

### Data Flow

```
LLM Stream Start
    |
    v
streamText() streams chunks --> yield to client
    |
    v
Stream Complete --> onFinish({ usage: { inputTokens, outputTokens, totalTokens } })
    |
    v
createUsageMetric() --> INSERT INTO usage_metrics
    |
    v
Message status = 'complete'

Error Path:
streamText() error --> onError({ error })
    |
    v
logAIError() --> console.error + optional webhook
    |
    v
updateMessage(status: 'error', metadata: { error })
```

### Why This Structure

- **observability.ts отдельно от workflows** — Single Responsibility, можно тестировать изолированно
- **usage_metrics отдельная таблица** — Позволяет: aggregate по assistant/user/model, retention policy отдельно от messages, dashboard queries без join с content
- **Callbacks в streamText, не в wrapper** — SDK гарантирует вызов после completion, не нужно отслеживать stream state вручную

### Invariants

1. **onFinish вызывается только при успешном completion** — не при abort, не при error
2. **usage_metrics.message_id NULLABLE** — для tracking без привязки к конкретному сообщению
3. **Token counts stored as-is** — totalTokens may exceed inputTokens + outputTokens when reasoning tokens present; all three values stored for accurate billing (Decision Log: Token count handling)
4. **Validation: non-negative tokens** — reject if any token count is negative or null; accept totalTokens >= inputTokens + outputTokens (reasoning tokens valid)

### Tradeoffs

| Choice | Gain | Cost |
|--------|------|------|
| Separate table | Clean analytics, independent retention | Extra table, extra INSERT per message |
| Property-based tests | Edge case coverage | Longer to write, harder to debug failures |
| Modular observability | Extensible, testable | Extra file, indirection |

+-- Phase 1: Observability - Usage metrics tracking
+--
+-- Separate table for analytics: enables clean aggregation queries
+-- without joining message content. Retention: indefinite for historical
+-- cost analysis (Decision Log: Retention policy).
+
+CREATE TABLE usage_metrics (
+  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
+  -- CASCADE DELETE: privacy compliance over analytics preservation
+  -- (Decision Log: CASCADE DELETE for metrics). When conversation deleted,
+  -- metrics also removed for GDPR-style data minimization.
+  conversation_id UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
+  -- message_id nullable: allows tracking usage without specific message binding
+  message_id UUID REFERENCES messages(id) ON DELETE CASCADE,
+  model TEXT NOT NULL,
+  -- CHECK >= 0: token counts are always non-negative by LLM API contract.
+  -- total_tokens may exceed input_tokens + output_tokens (reasoning tokens).
+  -- Decision Log: Token count handling - store all three as-is.
+  input_tokens INTEGER NOT NULL CHECK (input_tokens >= 0),
+  output_tokens INTEGER NOT NULL CHECK (output_tokens >= 0),
+  total_tokens INTEGER NOT NULL CHECK (total_tokens >= 0),
+  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
+);
+
+-- Index for conversation-level aggregations (cost tracking dashboard queries)
+CREATE INDEX idx_usage_metrics_conversation_created
+  ON usage_metrics(conversation_id, created_at DESC);
+
+-- Partial index: only when message_id exists (reduces index size)
+CREATE INDEX idx_usage_metrics_message_id
+  ON usage_metrics(message_id)
+  WHERE message_id IS NOT NULL;
+

+export interface TokenTrackerOptions {
+  client: SupabaseClient<Database>;
+  conversationId: string;
+  messageId?: string | null;
+  model: string;
+}
+
+/**
+ * Creates onFinish callback for Vercel AI SDK streamText.
+ *
+ * Automatically persists token usage when LLM stream completes successfully.
+ * Does NOT fire on abort or error (Invariant #1).
+ *
+ * @param options - Database client, conversation/message IDs, model name
+ * @returns onFinish callback compatible with streamText({ onFinish })
+ *
+ * SDK auto-aggregates usage, reducing tracking code.
+ */
+export function createTokenTracker(options: TokenTrackerOptions) {
+  const { client, conversationId, messageId, model } = options;
+
+  return async (result: { usage?: { promptTokens: number; completionTokens: number; totalTokens: number } }) => {
+    if (!result.usage) {
+      // Warn not error: SDK contract guarantees usage, but defensive
+      console.warn('[Observability] onFinish called without usage data');
+      return;
+    }
+
+    const { promptTokens, completionTokens, totalTokens } = result.usage;
+
+    try {
+      await createUsageMetric(client, {
+        conversationId,
+        messageId: messageId ?? null,
+        model,
+        inputTokens: promptTokens,
+        outputTokens: completionTokens,
+        totalTokens,
+      });
+    } catch (error) {
+      // Silent failure: observability failure should not break user-facing flow
+      console.error('[Observability] Failed to save usage metric:', error);
+    }
+  };
+}
+
+/**
+ * Creates onError callback for Vercel AI SDK streamText.
+ *
+ * Logs LLM-level errors (rate limits, model unavailable).
+ * Workflow errors (DB, abort) are handled by existing catch blocks.
+ *
+ * Structured format (timestamp, level, context, message, stack, metadata)
+ * enables monitoring tool integration (CloudWatch, Sentry). Consistent
+ * format across all LLM error paths (Decision Log: Error log structure).
+ *
+ * @param context - Optional context label for error logs
+ * @returns onError callback compatible with streamText({ onError })

+export function createErrorLogger(context?: string) {

+  };

+            totalTokens: fc.integer({ min: 0, max: 200000 }),

+            const tracker = createTokenTracker({

+              model: 'gpt-5-mini',

+     * Should warn (not throw) and skip metric creation.

+    it('handles missing usage gracefully', async () => {

+        model: 'gpt-5-mini',

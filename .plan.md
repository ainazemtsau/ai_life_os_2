# Remove Browser Verification, Strengthen Integration Tests

## Overview

Remove browser-based verification (Playwright MCP, browser_navigate, browser_console_messages, server launch) from the workflow and replace with mandatory integration test requirements. Integration tests must verify all cross-package interactions and API/Database operations using real dependencies (testcontainers, Supabase Docker). Unit tests use property-based approach with fast-check.

## Planning Context

### Decision Log

| Decision | Reasoning Chain |
|----------|-----------------|
| Remove browser verification entirely | Browser checks are flaky + require running dev server -> integration tests are deterministic and run in CI -> removing browser simplifies workflow while maintaining verification rigor |
| Replace with mandatory integration tests | Browser checked runtime behavior -> integration tests with real deps achieve same goal -> testcontainers/Docker provide isolated, reproducible environment -> same confidence, better reliability |
| Property-based unit tests | User selected -> fast-check covers many input variations with fewer tests -> catches edge cases humans miss -> higher coverage with less maintenance |
| Real dependencies for integration | User selected testcontainers/real services -> mocks hide integration bugs -> real Supabase via Docker catches actual failures -> same env as production |
| Remove Playwright MCP from settings | User confirmed removal -> no browser testing means Playwright MCP unused -> dead config should be removed -> cleaner settings file |
| MUST (not SHOULD) for integration tests | User chose strict approach B -> integration tests are blocking gate -> weak requirements defeat purpose of removing browser -> strong enforcement ensures coverage |

### Rejected Alternatives

| Alternative | Why Rejected |
|-------------|--------------|
| Keep Playwright for optional verification | User explicitly wants it removed; mixing verification methods creates confusion |
| Minimal change (remove browser, no new requirements) | Doesn't strengthen verification; defeats user's stated goal |
| Hybrid/gradual transition | User chose strict approach; gradual rollout delays benefits |
| Mocked integration tests | User chose real dependencies; mocks hide integration bugs |

### Constraints & Assumptions

- Vitest already configured in packages (ai, supabase, web)
- Docker Compose available (docker-compose.yml exists)
- Supabase runs in Docker for local dev
- fast-check available for property-based tests
- executor.py step 9 is the blocking verification gate
- CLAUDE.md instructions are in Russian - maintain language consistency

### Known Risks

| Risk | Mitigation | Anchor |
|------|------------|--------|
| Integration tests slow down workflow | Parallel execution via vitest --pool=threads; Supabase container reuse across tests | N/A - new implementation |
| Missing test coverage on first use | executor.py step 9 will block until integration tests exist for affected packages | .claude/skills/scripts/skills/planner/executor.py:148-211 |
| Existing tests may not cover interactions | Document required interaction coverage in structural.md | .claude/conventions/structural.md:75-118 |

## Invisible Knowledge

### Architecture

```
Verification Flow (After Change):

User Code Change
       |
       v
+------------------+
| Static Checks    |  type-check, lint, build
+------------------+
       |
       v
+------------------+
| Unit Tests       |  property-based (fast-check)
+------------------+
       |
       v
+------------------+     +------------------+
| Integration Tests| --> | Real Dependencies |
+------------------+     | Supabase Docker   |
       |                 +------------------+
       v
   PASS/FAIL (step 9 gate)
```

### Why This Structure

- Browser verification removed because it requires dev server running, is timing-sensitive, and cannot run in CI
- Integration tests replace browser checks because they verify the same interactions (API -> DB, cross-package) in a deterministic way
- Step 9 remains BLOCKING because verification rigor must be maintained

### Invariants

- Step 9 verification cannot be skipped - it gates all task completion
- Integration tests MUST cover: API routes + Database, All cross-package interactions
- Property-based tests MUST be used for unit tests where applicable

### Tradeoffs

- Removing browser checks loses visual verification capability (acceptable - not needed for most changes)
- Requiring real dependencies makes tests slower but more reliable
- Strict MUST enforcement may slow initial development until test patterns established

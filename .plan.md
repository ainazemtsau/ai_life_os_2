# UI Consistency System: Design Tokens + Property-Based Testing

## Overview

The chat UI components in `packages/ui/src/components/chat/` suffer from fragile styling due to hardcoded Tailwind values scattered across files. After implementing the edit feature, UI broke - sections became misaligned, colors inconsistent, and frames appeared on messages.

This plan establishes a design token system with TypeScript exports and CSS variables, migrates existing chat components to use tokens, and adds property-based tests to catch styling regressions. The system ensures future changes maintain visual consistency while providing type-safe APIs for developers.

## Planning Context

### Decision Log

| Decision | Reasoning Chain |
|----------|-----------------|
| TypeScript + CSS variables for tokens | Need both IDE autocomplete for DX and CSS var() for runtime flexibility -> pure TS lacks runtime theming, pure CSS lacks type safety -> hybrid provides both benefits |
| Single tokens.ts file (not per-component) | Chat components share identical colors/spacing -> splitting creates duplication + sync burden -> single source of truth reduces maintenance |
| Semantic token names (userBubble not zinc700) | Color values may change, semantic meaning persists -> hardcoded zinc700 requires find-replace for theme changes -> semantic names isolate value from usage |
| Property-based tests over visual regression | User chose DOM assertions over visual tests -> property-based validates invariants (colors match tokens, spacing consistent) -> catches regressions without snapshot maintenance |
| Migrate all chat components now | Partial migration creates two styling systems -> cognitive overhead for developers deciding which to use -> full migration establishes single source of truth |
| Focus ring uses design system color | Edit form uses hardcoded blue-500 -> inconsistent with globals.css --ring variable -> standardize on token to enable future theming |
| Spacing scale as explicit tokens | mb-4, mt-1, mt-2, p-4 scattered without rationale -> documenting as named tokens (messageGap, actionGap) explains purpose -> easier to maintain consistent spacing |
| group-hover pattern documented as invariant | MessageActions requires parent group class -> undocumented, fragile to refactoring -> explicit documentation + test prevents silent breakage |
| Storybook for component preview | User confirmed wanting Storybook -> enables isolated development and visual verification -> prevents need to run full app for component changes |
| OLED-optimized colors (user-specified) | User confirmed targeting OLED displays -> pure blacks (zinc-950/black) reduce power consumption on OLED -> chose dark black over dark gray for battery efficiency and stylish appearance |
| Zinc shade hierarchy for emphasis | zinc-700 (user bubbles): highest visual emphasis, brighter against black background -> zinc-900 (assistant bubbles): recedes into background, less prominent -> zinc-800 (secondary actions, borders): medium emphasis for supporting UI |
| Separate primary/secondary action tokens | Save actions are high-emphasis (user commits changes), Cancel actions are low-emphasis (user abandons changes) -> visual hierarchy guides user toward/away from actions -> separate tokens enable distinct styling (brighter primary, muted secondary) |
| Assistant bubble uses zinc-900 for neutral dark background | Assistant bubbles require neutral dark background matching OLED palette -> gray-700 variants have blue tint inconsistent with zinc-based color scheme -> zinc-900 provides neutral darkness matching user bubble zinc-700 hierarchy without color contamination |
| globals.css managed outside plan scope | Plan focuses on TypeScript token system -> CSS variables enable future theming but require manual sync -> establishing TS tokens first, CSS variable integration is separate concern |
| Token value format as stable API | Tests verify token usage by parsing .value strings -> changing format breaks tests and consuming code -> 'prefix-class' pattern documented as stable API contract for compatibility |

### Rejected Alternatives

| Alternative | Why Rejected |
|-------------|--------------|
| CSS modules for scoped styling | Project uses Tailwind exclusively -> mixing paradigms increases complexity -> stay consistent with existing patterns |
| Chakra/MUI component library | Heavy dependencies, different styling approach -> would require rewriting all components -> overkill for current scope |
| Visual regression testing (Chromatic) | User chose DOM assertions over visual tests -> adds CI complexity and cost -> property-based tests provide sufficient coverage |
| CVA (class-variance-authority) | Adds dependency for variant management -> current components have simple variants (user/assistant) -> inline cn() sufficient for now |
| Tailwind plugin for token enforcement | Build-time complexity -> lint rules simpler to implement -> can add later if needed |

### Constraints & Assumptions

- Tailwind is the only styling approach (no CSS modules, styled-components)
- Dark mode only currently (no light mode variants needed)
- UI package scanned by apps/web tailwind.config.ts for content
- globals.css :root CSS variables (--color-user-bubble through --color-secondary-action) must exist for .var token properties to work at runtime
- globals.css CSS variable definitions are maintained manually outside this plan's scope - this plan establishes TypeScript tokens only
- Token .value format is stable API contract: 'prefix-class' pattern (e.g., 'bg-zinc-700') will not change without major version bump
- Testing framework: Vitest + fast-check for property-based tests
- Storybook will be added for component preview
- Applied default-conventions domain="testing": property-based for unit tests
- Message IDs are always non-empty strings when present (empty string IDs not allowed in domain model)

### Known Risks

| Risk | Mitigation | Anchor |
|------|------------|--------|

## Invisible Knowledge

### Architecture

```
packages/ui/src/
├── theme/
│   ├── tokens.ts      # Single source of truth for design tokens
│   └── index.ts       # Re-exports
├── components/chat/
│   ├── message-bubble.tsx   # Uses tokens.colors.userBubble, etc.
│   ├── message-actions.tsx  # Uses tokens.colors.actionHover
│   ├── message-edit-form.tsx # Uses tokens.colors.focus
│   └── ...
└── stories/
    └── chat/
        ├── MessageBubble.stories.tsx
        └── ...
```

### Data Flow

```
tokens.ts (source of truth)
    │
    ├──> TypeScript imports (compile-time type safety)
    │       components import { colors, spacing } from '@/theme/tokens'
    │
    └──> CSS variables (runtime flexibility)
            :root { --color-user-bubble: #3f3f46; }
            components use bg-[var(--color-user-bubble)]
```

### Why This Structure

**Why single tokens.ts**: All chat components share the same visual language. Splitting tokens per-component creates sync burden. Single file ensures changes propagate everywhere.

**Why theme/ directory**: Separates design system from component logic. Tokens are foundational - they belong in their own module, not buried in a component.

**Why hybrid TS + CSS var**: TypeScript provides autocomplete and type errors for wrong token names. CSS variables enable future runtime theming (light/dark toggle) without rebuilding.

### Invariants

1. **MessageBubble must have `group` class** - MessageActions uses group-hover:opacity-100 pattern. Removing group class makes action buttons permanently invisible.

2. **Flex layout controls message alignment** - justify-end for user, justify-start for assistant. Changing to other flex values breaks message positioning.

3. **All colors must come from tokens** - Hardcoded colors (bg-zinc-700, bg-gray-600) are forbidden. Only token-derived classes allowed.

4. **Spacing uses named tokens** - mb-4 for message gap, mt-1 for action gap, etc. Direct spacing values only when token doesn't exist.

5. **Token .value format stability** - Token .value properties return 'prefix-class' strings (e.g., 'bg-zinc-700'). This format is API contract and must not change without major version bump. Tests and consuming code depend on this pattern.

### Tradeoffs

| Choice | Benefit | Cost |
|--------|---------|------|
| Hybrid TS+CSS tokens | Type safety + runtime flexibility | Slightly more complex token definitions |
| Migrate all components now | Immediate consistency | Larger initial change set |
| Property-based tests | Wide input coverage | Learning curve for fast-check |
| No visual regression | Simpler CI, no snapshot maintenance | May miss subtle visual issues |
